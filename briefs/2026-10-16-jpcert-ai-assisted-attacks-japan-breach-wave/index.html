PIR-1: yes, but not in the alert. JPCERT/CC's alert of 8 October (JPCERT-AT-2026-0030) never mentions AI (C-001). The AI statement appears a week later, on 15 October, in a JPCERT/CC Eyes blog post by its Attack Infrastructure Investigation Team. It says JPCERT "confirmed" that attackers used AI to scan for known vulnerabilities and attack via APIs (C-002). The text gives no basis for that word. The basis is in the figures: open directory listings on attacker servers that hold configuration for AI coding agents ( .claude/ , .claude.json , .qwen/ , .codex/ , .cc-switch/ ) (C-003). We judge it likely that at least some of the wave's operators used AI coding agents (C-004). That rests on one team's infrastructure finding, plus a second vendor's agent detection on IPs that do not overlap JPCERT's. It does not show the agents did the breaching. PIR-2: four Japanese organisations publish TTPs and indicators: JPCERT/CC, Macnica with ITOCHU Cyber & Intelligence and SecureSky, NICT LETTICE, and Cyber Security Cloud. A fifth, BitForest Scutum, publishes AI-agent detections. Together they give 19 IPs, 14 User-Agents, 6 JA4 fingerprints, one CVE and a file-level picture of the attacker servers. [Redacted] audit every backend API that a public mobile app calls.

Key judgements

  • (almost certain) JPCERT/CC's only claim of AI use in this wave is the 15 October blog, not the 8 October alert (C-001, C-002). English-language coverage that credits "JPCERT's alert" with an AI finding is wrong about the source.
  • (almost certain) The visible basis for JPCERT's claim is AI coding-agent configuration on attacker-controlled servers: Claude Code (.claude/, .claude.json), Qwen Code (.qwen/), OpenAI Codex CLI (.codex/) and CC Switch (.cc-switch/), a tool for switching Claude Code and Codex providers (C-003). JPCERT never names these tools; we read them from its figures.
  • (likely) At least some operators of the wave used AI coding agents for reconnaissance and API attacks (C-004, H-001). The agent detection comes from a single team (JPCERT). Scutum separately detected AI agents on three IPs between 10 and 14 October (C-008), but those IPs overlap none of JPCERT's, and Scutum itself saw none of the wave's mobile-app signature. Cyber Security Cloud's "AI agent" reading is explicitly inference from behaviour (C-007).
  • (likely) AI did not find new zero-days here. The wave exploits basic access-control, authentication and configuration flaws in each target's own APIs, plus known CVEs (C-006, single-sourced to the Macnica/ITOCHU/SecureSky IR team as of 6 October).
  • (very likely) The core technique is what NICT calls the "A2B attack" (App-to-Backend). Attackers decompile public Android and Flutter apps (from Google Play, Japan region) to recover API endpoints, keys and signing logic, then call the backend directly (C-009). Three organisations report this independently.
  • (likely) 210.149.87[.]120, 69.10.51[.]162 and 207.241.172[.]54 look like one operator's build: dedicated VPS with the same port profile, tagged c2, the first two also open-dir (C-015, #4, #6, #11). These are the three IPs that more than one publisher lists.
  • (unlikely) "Japan declared a cyberspace emergency" (C-011) rests on one tier 3 article. The primary record shows an inter-ministry meeting on 8 October and an LDP party meeting on 9 October (C-014). Do not repeat the "emergency declaration" framing.

Findings

What each authority said about AI (PIR-1). Checked against the raw page or PDF, never against a summary:

  • JPCERT/CC alert, 8 Oct, updated 9 Oct (S-001). No mention of AI. A regex sweep for AI, 生成AI, 人工知能 and LLM returned zero hits (C-001).
  • JPCERT/CC Eyes blog, 15 Oct (S-002). Verbatim: 「その過程で、攻撃者がAIを利用して、既知の脆弱性のスキャンやAPI経由での攻撃などを実施していたことを確認しました。」 Translation: "In the course of [investigating attack infrastructure with several organisations], we confirmed that the attackers were using AI to carry out scanning for known vulnerabilities, attacks via APIs, and the like." No English edition exists (blogs.jpcert.or.jp/en/... returns 404) (C-002).
  • Macnica / ITOCHU Cyber & Intelligence / SecureSky, 7 Oct (S-003). In section 10, which the authors mark as their own speculation: 「一連の事案でAIが使われたと断定できるログや痕跡は確認されていません」 ("no log or trace that conclusively shows AI was used has been found"). They add that AI use is "harder to deny than to assert", given the breadth of per-site probing (C-005).
  • NICT LETTICE, 13 Oct (S-004). AI appears only as a general concern: AI is making program analysis and vulnerability discovery more efficient. NICT never says it observed AI.
  • Cyber Security Cloud, 9 Oct (S-005). "Possibly an AI agent", because the traffic was too heavy for a human yet had no tool-like regularity and adapted to each response. The firm adds that this is "inference from behaviour, not a trace that directly shows AI use" (C-007).
  • BitForest Scutum, 14 Oct (S-006). Changed its WAF's behaviour on the night of 10 October to tell AI agents from scripted tools. It reports AI-agent attacks from 3 IPs by 14 October and claims near-zero false positives, tested against 8 recent models including Qwen and GLM. The method is withheld (C-008).
  • National Cybersecurity Office, 9 Oct (S-008). Generic wording only, on page 4: attack methods "including AI misuse" are growing more sophisticated (C-013).
  • Adjacent, not this wave. Cisco Talos (S-009) found AI-generated Python in a Qilin open directory (deadman.py, veeam_kill.py, deploy_locker.py, rated medium-to-high), covering January to July 2026 ransomware in Japan (C-012, single-sourced to Talos). The Qilin and this wave share an "open directory with AI artefacts" pattern, and nothing more.

Assessment

Three hypotheses are registered (hypothesis matrix). The registered evidence records only discriminate H-003 (benign shared IPs). They favour it for the cloud, shared-host and NAS addresses (#1, #2, #3, #8, #9, #10, #14) and count against it for the four dedicated open-dir/c2 VPS (#4, #6, #11, #16). The records are declared silent on H-001 versus H-002, because port data cannot show what drove the traffic.

The discriminators between H-001 (AI agents drove the attacks) and H-002 (AI present but incidental) are in the reporting:

  • For H-001. JPCERT's figures show agent configs in the same home directories as the attack working files (brute3.py, auto_login.py, admin_api.sh, apk_dex/). The files sit side by side, not on a separate host. Scutum built a detector aimed at exactly this question and reports positives. Cyber Security Cloud's 5-stage adaptive flow is what an agent loop looks like.
  • For H-002. The working-file names (pw2.py, pw3.py, brute3.py, setup13.sh) look like iterative human-and-assistant work, not an autonomous pipeline. Both are possible. A config directory proves installation and login, not use against a target. Scutum's IPs are not the wave's IPs, and one of them only ran a plain 404 scan. CSC's reading is self-declared inference.

Net: H-001 is likely and stays open. It moves to "very likely" only if a second team with its own access (an IR firm, or the AI providers' own abuse reporting) ties agent sessions to traffic from the wave's listed IPs.

Whether AI was used does not change the defence. Every source agrees the wave exploits basic API authorization and secret-handling flaws, at a speed and breadth that make "nobody will find our internal API" untrue.

Key assumptions

  • The three Appendix B IPs host the directories in JPCERT's figures. If wrong, the open-dir/c2 cluster (C-015) is still real, but it stops being the AI evidence's home.
  • The figures show attacker-controlled hosts, not compromised third-party servers. JPCERT calls them 攻撃元サーバー ("attack-source servers"). If any were hijacked, the agent configs could belong to the hijacked owner, and C-003 would weaken sharply for that server.
  • Macnica's 265-case count and the JPCERT cases describe one wave. Macnica excludes cases it ascribes to other clusters. If it is several crews, "the wave used AI" can be true of one crew only. That is the reason C-004 says "at least some".

Association scoring

Not performed. No named group is in play, and no source attributes the wave. The police chief said on 8 October that the background and the links between incidents are unknown.

Hunts and controls

Immediate exposure checks

  • Search 60 days of API gateway, WAF, reverse-proxy and app-server logs for the 19 IPs above, the Metabase-GHSA-vwf4/2.0 UA, and the six JA4 values. Treat a hit as a lead, then read the requests around it.
  • Search for production mobile-app API keys or request signatures arriving with a non-app User-Agent (curl, python-requests, Dart/*, a bare Dalvik/2.1.0, sqlmap).
  • Search egress logs for backend-originated requests whose URL contains /r302?u=, or any backend fetch of an external IP that returns a 302 to RFC1918 space or 169.254.169.254.

Behavioural hunts

  • Find the same account, session token or device ID seen from more than 20 IPs in one hour. Hunting by IP misses this wave.
  • Watch auth and lookup endpoints for responses whose size falls outside the known success/failure sizes. Watch per-endpoint 4xx/5xx/429 bursts, especially on internal APIs the UI never calls.
  • Flag accounts created or role-changed through the API with no matching UI flow.
  • On app servers, alert on new .war deployments, and on java spawning sh/bash/cmd.
